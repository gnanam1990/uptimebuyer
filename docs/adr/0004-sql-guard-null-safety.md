# ADR 0004 — SQL guards must be NULL-safe

Status: accepted (M07 security forward fix, 2026-11-05)

## Context

Database guards are the backstop for every service-layer check (ADR 0001 decision 2): they must hold for a caller that
bypasses the service. Most guards are PL/pgSQL triggers of the form `IF <cond> THEN RAISE` or
`IF NOT (<cond>) THEN RAISE`. SQL uses three-valued logic: when `<cond>` evaluates to NULL, `IF` treats it as false
and the RAISE is skipped. A guard written as "raise when not allowed" therefore **fails open** whenever "allowed"
can be NULL.

This happened in `ub_contact_point_usable_guard` (`0013_m07_contact_point_review.sql:49`), the database backstop for
the M07 contact-point destination-hijack fix:

```sql
IF NOT (latest = 'VERIFIED' OR (latest IS NULL AND cp.intake_state = 'DISCOVERED'
        AND cp.source_provider_account_revision_id = NEW.provider_account_revision_id)) THEN RAISE ...
```

With no review row, `latest = 'VERIFIED'` is NULL, so any non-TRUE second branch makes the whole condition NULL.
Direct SQL inserts were accepted for an unreviewed `PENDING_REVIEW` point, an unreviewed point with a NULL source
revision (legacy or pre-0013 rows) and an unreviewed point from another account revision. Only a REJECTED review was
refused. The regression test is `packages/providers/test/t029-contact-point-guard-null-safe.int.test.ts` (red: 3 of 8
failing before the fix).

## Decision

1. **Every RAISE guard must be NULL-safe.** The RAISE must fire unless the allowed condition is definitely TRUE.
   Accepted shapes:
   - `IF coalesce(<allowed>, false) IS NOT TRUE THEN RAISE` (preferred for allow-list guards);
   - `IF NOT EXISTS (SELECT 1 ... WHERE <allowed>) THEN RAISE` (a NULL predicate excludes the row, so it fails closed);
   - "allowed → RETURN NEW, otherwise RAISE" (a NULL falls through to the RAISE);
   - comparisons written with `IS [NOT] DISTINCT FROM`, `IS [NOT] NULL`, `FOUND` or `EXISTS`;
   - plain `=`, `<>`, `<`, `>`, `IN`, array operators or SQL helpers only when every operand is provably non-NULL
     (NOT NULL column, `count(*)`, `EXISTS`, `coalesce`, or a row whose existence was just checked). A NOT NULL column
     of `NEW` counts: NOT NULL constraints are checked after BEFORE triggers, so a NULL there is still rejected.
2. A guard that reads a row with `SELECT ... INTO` must handle "no row" explicitly (`IF NOT FOUND THEN RAISE`) unless a
   later NULL-safe comparison already refuses it.
3. A "raise when a bad row exists" guard (`IF EXISTS (SELECT 1 ... WHERE <bad>)`) is the dual hazard: a NULL `<bad>`
   hides the row. It is acceptable only when the compared columns are NOT NULL or compared with `IS DISTINCT FROM`, and
   a missing parent is left to a non-deferred composite foreign key.
4. CHECK constraints pass on NULL by design. A CHECK on a nullable column is flagged only when NULL would bypass a
   security rule.
5. Fixes ship as forward migrations (`CREATE OR REPLACE FUNCTION`); applied migrations are never edited. Behaviour for
   non-NULL inputs stays identical.

Migration `0017_m07_contact_point_guard_null_safe.sql` redefines the contact-point guard with
`coalesce(..., false) IS NOT TRUE` and an explicit `IF NOT FOUND` refusal (same UB075 message, so the guard does not
distinguish a missing point from an unapproved one).

Summary: 34 trigger/guard functions plus one guard DO block audited. 1 UNSAFE and reachable (fixed in 0017), 1 SAFE
but latent (unreachable, documented), all others SAFE. SQL helpers are NULL-propagating but every call site passes
non-NULL operands. Two CHECK constraints pass on NULL; neither bypasses a security rule.

## Static tripwire

`packages/data/test/t009-guard-null-safety.test.ts` (unit) scans migrations numbered 0017 and later for a negated
`IF NOT ( ... ) THEN` guard whose condition does not contain `coalesce(` or `IS [NOT] DISTINCT FROM`, and fails on any
hit. It is deliberately narrow so it stays low-noise: run over 0000–0016 it finds exactly two conditions, the 0013 bug
and one false positive (`0011:298`, array containment on non-NULL operands). It does not catch an unguarded
`IF a <> b THEN RAISE`, `IF NOT helper(...)` or deny-list `EXISTS` with nullable columns; those stay a review rule
(this ADR) because a regex cannot tell nullable from NOT NULL operands.

## Consequences

- New guards use the shapes above; reviewers check operand nullability against the table definitions.
- A guard fix is a new forward migration with a direct-SQL regression test that bypasses the service layer.
